## Roles and Responsibilities

### Project Lead

- Set project direction and roadmap
- Review and merge pull requests
- Manage releases
- Coordinate with contributors
- Ensure project quality

### Core Maintainers

- Review pull requests
- Triage issues
- Write and review documentation
- Mentor new contributors
- Participate in discussions

### Contributors

- Submit pull requests
- Report bugs
- Suggest enhancements
- Improve documentation
- Help other users

## Becoming a Maintainer

### Requirements

To become a maintainer, you should:

1. **Have a track record of contributions**
   - Multiple merged pull requests
   - Consistent quality contributions
   - Good understanding of the codebase

2. **Demonstrate expertise**
   - Deep knowledge of the project
   - Ability to review code effectively
   - Understanding of best practices

3. **Be active and responsive**
   - Regular participation in discussions
   - Timely response to issues and PRs
   - Availability for critical issues

4. **Align with project values**
   - Commitment to code quality
   - Respectful communication
   - Collaborative approach

### Process

1. **Nomination**: Existing maintainers can nominate candidates
2. **Review**: Core team reviews the candidate's contributions
3. **Vote**: Core team votes on the nomination
4. **Invitation**: If approved, the candidate is invited
5. **Onboarding**: New maintainer receives access and guidance

## Communication Channels

- **GitHub Issues**: Bug reports and feature requests
- **GitHub Discussions**: General discussions and questions
- **Pull Requests**: Code review and collaboration
- **Email**: security@planmanage.com (security issues only)

## Decision Making

### Consensus-Based

- Most decisions are made by consensus
- Maintainers discuss and agree on changes
- Disagreements are resolved through discussion

### Voting

For significant decisions:

- Each maintainer gets one vote
- Majority wins
- Project lead has tie-breaking vote

### Lazy Consensus

For minor changes:

- Propose the change
- Wait for feedback (48 hours)
- If no objections, proceed

## Release Process

### Version Numbering

We follow [Semantic Versioning](https://semver.org/):

- **Major** (X.0.0): Breaking changes
- **Minor** (0.X.0): New features, backward compatible
- **Patch** (0.0.X): Bug fixes, backward compatible

### Release Steps

1. **Prepare release**
   - Update CHANGELOG.md
   - Update version numbers
   - Run all tests
   - Build and verify

2. **Create release**
   - Create release branch
   - Final testing
   - Create GitHub release
   - Publish to npm (if applicable)

3. **Post-release**
   - Announce release
   - Monitor for issues
   - Address critical bugs

## Code of Conduct

All maintainers must follow our [Code of Conduct](CODE_OF_CONDUCT.md). This includes:

- Using welcoming and inclusive language
- Being respectful of differing viewpoints
- Gracefully accepting constructive criticism
- Focusing on what is best for the community
- Showing empathy towards other community members

## Removing Maintainers

Maintainers may be removed if they:

- Violate the Code of Conduct
- Become inactive for an extended period
- Are unable to fulfill their responsibilities
- Request to step down
